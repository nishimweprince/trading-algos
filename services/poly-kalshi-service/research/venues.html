Where the strategy should look next

A ranked map of short-duration crypto prediction markets, settlement compatibility, execution constraints, and where each adapter should run for the lowest defensible end-to-end latency.

Research complete

Decision

Build record-only adapters in this order: Gemini → OKX → Nadex/CDNA → Predict.fun → Polymarket US → Jupiter/BisonFi. Keep broker, parimutuel, and fixed-quote markets outside the current active-exit engine.

Gemini Predictions

Build first

Native recurring 15-minute BTC, ETH, SOL and XRP binaries; public event discovery; public book, depth, trade and index streams; plus REST/WebSocket trading. This is the strongest combination of asset overlap, real order-book microstructure and integration quality found.

Correlated is not equivalent

Gemini’s reference index and equality rule differ from the Kalshi and Polymarket contracts. Capture the exact source and sample rules before using it as anything stronger than an E1 signal leg.

Contract equivalence

Store the grade with every matched contract. The new candidates initially belong in E1, not E0.

E0 · Equivalent

Same outcome, source, time window, tie rule and correction policy. Eligible for true cross-venue pricing logic.

E1 · Correlated

Same clock and direction but a different oracle, strike, sample, tie rule or correction policy.

E2 · Related

Same underlying with a different timeframe, threshold or contract shape. Signal use only.

E3 · Reference

Spot, perp, options, broker quotes or play-money forecasts. Never an executable twin.

Frontends are not extra liquidity

Coinbase predictions route to Kalshi; Binance Wallet predictions route to Predict.fun; Crypto.com Predict Pro, CDNA, OG Predictions and Nadex belong to one exchange family; Jupiter’s Kalshi/Polymarket listings are aggregations.

Implementation shape

Follow the isolated pk-limitless pattern and normalize contract semantics before quotes.

01Discover

Poll catalogs and persist full contract rules and venue IDs.

02Record

Store raw frames, normalized BBO and settlement-source observations.

03Measure

Run at least 72 hours; compare coverage, depth, lead/lag and disagreements.

04Paper

Model fees, latency, partial fills, speed bumps and locked positions.

05Promote

Enable live only after venue limits, stale-feed checks and kill switches pass.

Adjacent FX path

Kalshi’s 15-minute EUR/USD, GBP/USD and USD/JPY contracts form a second strategy family. Use OANDA, Saxo, LMAX or IBKR as price references—not as equivalent prediction venues—and test whether spot FX leads Kalshi.

Decision: add Virginia and Tokyo; keep Dublin

No single cloud region is optimal for this venue set. Use independent venue processes in AWS us-east-1, AWS ap-northeast-1, and the existing AWS eu-west-1 deployment. Publish normalized observations to the shared stream; do not put a cross-region coordinator synchronously in the order path.

Recommended worker footprint

This separates venue-documented infrastructure from live network observations and informed placement choices.

AWS us-east-1 · N. Virginia

US prediction worker

Gemini public REST/WebSocket, Polymarket US public REST/gRPC, and temporary CDNA probes. Kalshi alone is closer to its current us-east-2 origin; Gemini FIX belongs in Equinix NY5.

AWS ap-northeast-1 · Tokyo

Asia prediction worker

OKX, Predict.fun, Pascal and Hyperliquid. Predict.fun and Pascal publish this region; Hyperliquid’s Foundation low-latency node is in AZ1; the project has already measured OKX near 18 ms from Tokyo.

AWS eu-west-1 · Ireland

Polymarket-global worker

Keep the existing trader in Dublin: project measurements put the London CLOB path near 10 ms while Ireland remains usable for opening positions. Start Limitless here and measure before splitting it out.

Measure the order path, not the CDN

Before placement, run at least 24 hours from every candidate region and record market-event timestamp → receive, warm order probe → acknowledgement, acknowledgement → private update, disconnects, and p50/p95/p99 by UTC hour. For on-chain legs, add block arrival and signed transaction → inclusion. Promote a region only when end-to-end execution improves.
